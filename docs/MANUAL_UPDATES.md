# 手动更新

## 当前产品设计：没有平台回调也能核对结果（2026-10-12）

本节覆盖下方旧执行器交互设计。GPT负责网页/协议代码；Grok独立检索与发布。**没有平台状态回调，不等于可以假装完成。** 当前专用Webhook及密钥配置仍待授权，网页提供明确标注的“复制指令→用户发给X+github→按编号核对”过渡入口；不是已经实现一键送达。定时任务不改变。

### 用户体验

1. 更新本页 / 全部更新先弹窗，显示准确范围，不直接启动。轻松说明：“Grok出门找消息，可惜没带对讲机。我们不表演假进度条，只认带编号的结果。”
2. 未接通时展示完整可复制指令。复制≠发送；用户真正发送后，点击“我已在Grok发送，开始核对”。没有Grok权限的朋友可以把指令交给主人，不共享密钥。未来直连仅在服务端声明`delivery=grok-webhook`后开放，旧D1队列/在线心跳绝不冒充Grok接通。
3. 直连确认后只接受`{delivery:"grok-webhook",accepted:true}`作为入口受理；不声称运行中或完成。网络断开保留同一编号为“送达未确认”，不自动重发。服务端必须按编号幂等、同页面活动请求合并，同一Bot串行；未验收不得设置该能力标记。
4. 浏览器每15秒查询本次结果凭证；隐藏页面暂停，回来继续。使用请求编号、请求时间、完整页面范围及公开内容SHA-256核验，不用内容更新时间/Git提交时间认领定时任务。找到结果后刷新相应页面数据，不打断正在阅读的位置。
5. 30分钟未确认就停自动轮询，明确“未确认，不代表失败”；给出手动核对、复制同一编号问Grok、继续阅读。没有假的百分比和无限转圈，也不自动重复采集。已完成、部分完成、无高价值新增、失败分别展示。只允许用户显式重试失败页面，新编号保留原凭证；部分缺额不自动重采。
6. 关弹窗不取消后台工作；在本浏览器保存最近一个请求的编号/范围/时间/交接方式7天，不存密钥或聊天内容。换设备不承诺同步；可在原Grok对话按编号查询。浏览器禁用存储或剪贴板时明确提醒并提供手动复制。只有网页内提醒，不索要通知权限。
7. 已有待核对请求时两个更新按钮都回到该请求，不生成第二份。结束查看不等于取消，须明确确认；恢复或重试前先查Bot原任务。跨朋友/跨设备真正去重仍须接通服务端后验收，不把本机防连点当分布式锁。

### 运行位置规则（用户2026-10-12确认，唯一维护于此）

本接入及日常运行**完全在Grok云端与Cloudflare**完成，不依赖用户电脑：用户电脑不承担代码执行、本地服务器、队列消费者、采集、定时、发布或故障备用。旧本机执行器/`dev:updates`/`updates:start`不是备用方案。代码由GitHub推送触发Cloudflare Pages自动构建部署；D1绑定与密钥由用户在Cloudflare控制台设置。

### Webhook直连实现（2026-10-12，代码已完成，部署配置与端到端验收待完成）

- 链路：网页 → `/api/updates`（Cloudflare Pages `_worker.js`，管理登录Cookie、同源校验）→ D1 `webhook_requests` 幂等/去重 → POST 原生例行任务「intelbrief 网页手动更新（Webhook）」→ Grok独立采集发布 → v2凭证 → 网页核验。
- 仅派发 `{requestId,requestedAt,pages}`；页面白名单 news/people/tickers/ai/crypto；多余字段（含任意提示词）一律400。旧runner接口在此模式下404，不启用Codex。
- 只有当 `UPDATES_DB`、`UPDATE_ADMIN_KEY`、`GROK_WEBHOOK_URL`(https)、`GROK_WEBHOOK_KEY`、`GROK_WEBHOOK_AUTH_HEADER` 全部存在才声明 `delivery=grok-webhook`；任一缺失网页显示“未接通”并保留复制交接。`GROK_WEBHOOK_AUTH_HEADER` 原样作为 `Authorization` 头的完整值，取自例行任务面板“Authorization header”字段；**代码不拼接、不默认Bearer**。
- 同编号重复提交只返回已存记录，不再派发；30分钟内已有覆盖相同页面的活动请求则合并返回原编号（跨设备）；部分重叠返回409；全局一次只允许一个派发中。Webhook 2xx才返回`accepted=true`；非2xx返回502且不受理（网页换新编号可重试）；超时/网络错误记为“送达未确认”，同编号不自动重发。受理≠开始≠完成，完成只认v2凭证。
- 隔离测试 `test/webhook-updates.test.js` 使用假Webhook，不写data/、不产生公开凭证。

### Grok执行协议：v2结果凭证（必须遵循）

收到带编号的网页指令后，先安全拉取，读AGENTS/本节/各页SOP，检查同编号凭证及其他正在运行任务。若已有结果，只核对及报告，不重复检索。未完成任务保存实际断点，串行接续，失败阶段最多重试两次；没有平台回调不增加GPT消费者或新定时任务。

完成真实采集、检查和页面内容准备后，生成一个工作区外的结果JSON，示例如下（仅协议示例，禁止把示例当真实结果发布）：

```json
{
  "requestId": "原请求完整编号",
  "requestedAt": "原请求带时区时间，原样保留",
  "pages": ["news", "people"],
  "completedAt": "实际完成整理的带时区时间",
  "results": [
    {"page":"news","status":"partial","message":"本次实际条数及覆盖缺口"},
    {"page":"people","status":"failed","message":"实际失败原因；保留旧内容"}
  ]
}
```

- `complete`：全部要求的对象真实核验完毕且有合格新增；`unchanged`：实际核验完毕但没有高价值新增；`partial`：部分覆盖/证据缺额，明示缺口；`failed`：不能完成该页采集或发布。所有页面都须返回一项，不能漏项，不能将未查记成无新增。
- 运行 `npm run updates:receipt -- <结果JSON文件>`。此工具**只准备凭证**，自动计算各页文件摘要，写入 `data/update-receipts/<requestId>.json`；不采集、不提交、不推送。已有凭证不同则拒绝覆盖，同一请求只保留实际采用版本。
- `news`核对持久池及期次目录，其余四页核对对应情报JSON。失败项不带文件；无新增也要凭证及真实覆盖审计，不能只改内容时间。内容和凭证须同次提交发布，先test/check/build再明确暂存并推送。每次修改前pull规则不变。
- 推送后同时核对线上凭证和受影响内容。只有核对完成才向用户报告完成；部署失败优先复用已生成文件，不重采集、不篡改已冻结期次。网页找到凭证还会独立核验摘要。
- 若线上已被后续批次更新，旧凭证摘要不一致时网页保守显示“版本不一致”，而非认领新批次；Bot应按原编号检查Git中的原始发布与实际线上验收记录，给用户明确解释。这是目前实现的边界，不覆盖不可变凭证来消除提示。
- 凭证是公开网站资源，只含请求编号、页面范围、时间、简短结果、允许文件名和摘要；禁止放Token、用户身份、私有提示词、原始错误堆栈。旧v1凭证仅供历史，不当成新协议完成结果。

## 接通

### 本地调试模式

运行 `npm run dev:updates` 同时启动本地网站、持久化任务队列和执行器，打开 http://localhost:8787 。本机访问免登录，该模式仅用于调试执行器，数据只写入本机工作区；调试得到的数据若要保留，必须按 AGENTS.md 提交并推送。任务、断点和本机密钥位于 `~/.local/share/intelbrief-updates/local/`，与云端配置隔离；本地免登录仅在显式本地标记且主机名为回环地址时生效。停止命令后网页/执行器停止，重开命令恢复持久化记录。

### 云端接入

1. `npm ci`，然后 `npx wrangler login` 完成 Cloudflare 登录。
2. `npm run updates:setup`：创建或复用 `intelbrief-updates` D1，初始化表，配置 Pages 的 `UPDATES_DB` 绑定与两个密钥。脚本幂等复用本机配置，不打印密钥。
3. 在现有 Cloudflare Pages 项目确认构建命令为 `npm run build`、输出目录为 `dist`，部署本次代码。`wrangler.toml` 的 D1 绑定和输出目录作为部署配置；不得继续使用空构建命令。
4. `npm run deploy` 或推送 `master` 触发既有 Git 集成；确认 `/api/updates` 返回“登录后可更新内容”，而不是“更新服务尚未接通”。
5. `npm run updates:start` 启动本机执行器。它每15秒领取已提交任务，不自行扫描X、不新增定时简报。关闭此进程/电脑睡眠会显示执行端离线。常驻启动方式需在上线时落实，不把交互终端启动描述成开机自启。
6. 本机 `~/.local/share/intelbrief-updates/config.json` 的 `adminKey` 用于网站更新面板登录。文件权限600、目录700；不要粘贴到聊天、提交仓库或放进前端。网页使用30天的安全HttpOnly会话Cookie，不在localStorage保存密钥。
7. 先执行单页，再执行全部更新，抽查原帖证据、线上归档、失败和无新增状态，确认真实链路后再标记上线。

页面只接收固定页面标识，不能提交任意提示词或Shell命令。执行端使用独立密钥领取任务；它启动已登录的 `codex exec`，继承本机模型配置，限制为只读研究，再由普通Node程序校验与发布。采集来源统一遵守 [AGENTS.md](../AGENTS.md)：本机Grok Bot App固定使用「X+github」主执行Bot，失败才用Grok网页版；旧「推特信息获取」只保留历史，不再使用，也没有第三条路径。执行器关闭普通网页搜索，拒收其他获取路径的结果。登录或UI权限不可用必须如实显示，不能绕过。

执行器生成每个采集提示时，会读取 `config/research-guidance.json` 并把项目知识库与 Grok 采集 SOP 注入执行上下文。Grok 只接收由这些材料生成的公开检索问题，不接收知识库全文。美股讯息、具体人物、具体个股、AI板块与加密共用同一套追源、反证和降噪闸门（主题优先级见各页配置），避免不同触发方式产生两套标准。

## 归档与发布

- 手动简报以受理时间为信息截止，文件为 `manual-<任务编号>.json`；定时整点归档不变，均不可覆盖。定时窗口只参考以前的定时期次，手动更新不移动定时采集起点。
- 人物按账号记录检查时间。仅完整检查成功的账号推进时间，部分失败保留原断点；原帖按ID去重，保留完整人物时间线。人物更新不修改美股简报。
- 个股按 Tab 报告覆盖；schema 与人物情报事件库对齐。AI 任务（page=`ai`）写入 `data/ai-intelligence.json`；加密任务（page=`crypto`）写入 `data/crypto-intelligence.json`；均不得写入 tickers。
- D1限制每页一个活动任务、全局一个执行中的任务。重复点击复用任务，全部更新补上未提交页面。有效租约每20秒续期，过期执行端不能再写任务结果。
- 每个任务使用独立本机检出目录，只提交明确的数据文件。普通远端变更尝试rebase，冲突时保留证据并停止，不强推、不重置用户目录。
- 校验后保存发布断点。推送后逐个核对线上受影响JSON与本机内容；未确认发布不显示完成。发布失败重试复用断点，不重新采集。已发布的失败简报重试新建手动期次，保留失败历史。
- 无新增也保存真实检查记录；全部人物采集失败保留原数据，不冒充无新增。部分完成显示缺额/失败账号。
