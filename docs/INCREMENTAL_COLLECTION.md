# 增量采集与累计阅读（2026-10-18采用）

本文件是事实流时间接续、周末频率与本机运营的当前执行入口。个股独立热点按用户指定，每轮完整24h榜单，是严格增量的明确例外；其余来源与证据门槛不变。

## 三条用户要求

1. 事实对象严格从上次成功采集截止接到本次冻结截止；个股热点每次独立重查截止前24小时。
2. 北京时间工作日08:00/15:00/20:30，周六日各08:00一次；不新增后台扫描。
3. 搜索增量，展示累计。早上08:00的重要内容在晚上20:00仍可读；已展示不代表已读，无须每天读三遍。

## 进度不是卡片条数，也不是网站发布时间

`data/collection-progress.json`保存新闻7个主题及人物/个股/AI每个顶部Tab的独立进度。相同截止适用于一轮全部对象，原帖发布时间区间左闭右开。事件实际时间另存，不把发布时间当事件发生时间。

个股另有`tickers:<id>:hotspots`独立对象，和原`tickers:<id>`事实游标分离；采用`rolling-24h-snapshot`，每轮起点固定为截止前24小时、终点为本次截止，允许与旧榜窗口重叠。每股独立Expert短请求，不与事实任务混发；成功榜采用新结果而非旧池合并。`through`在此只表示最近成功榜单截止，失败不推进、不需要补搜14天旧热点。新只读「每日更新」不产生采集对象，不能混入检索批次。

- `searched`：按既定清单查询完成，候选已保存，即使全部证据不足也能推进；不表示搜尽X。
- `no-result`：实际执行查询、返回空，照常推进。
- `failed`：请求失败、未执行完清单或结果未保存，不推进该对象。下一轮仅从其旧截止接续补查。
- 候选来源不足与请求失败分开；待核候选记录在`pending`，不要让其他已完成对象重复宽搜。
- 手动与定时共用此进度。手动快照与定时快照各自保留上限不变。
- 必须先保存真实候选结果与执行审计，再运行进度记录。采集成功但发布失败，只重试已保存结果的发布，不重做采集。
- 第一次无进度对象才默认回查24小时；断档分连续最多14天的片段追赶，不跳过旧缺口，不假称已追到当前。
- 更改对象/查询范围应增加新的对象标识或明确登记补查，不沿用旧范围的成功证明。
- Grok延迟索引仍可能导致迟发现；已知缺口和补遗单列，保留原始时间，不混称本轮新增。严格接续不是零漏收保证。

迁移只从`2026-10-18-2030`既有执行审计建立20:30切换点：四批均保存了真实查询、完成的发现/追源/反证及对象清单。旧`partial`含义和历史覆盖记录不改写；切换点证明既定查询执行过，不证明全量X覆盖或候选全部可信。

## 每轮操作（本机任务唯一入口）

1. 检查分支、远端和改动，首次写入前`git pull --ff-only origin master`。只读必要且发生变化的规范，不每轮把整库重新读一遍。
2. 冻结本轮北京时间截止，运行`npm run collection:plan -- <CUTOFF>`。`scheduled=false`立即结束，不造期次。手动任务用`npm run collection:progress -- plan <CUTOFF>`取得同一套进度；不绕开周末降频自动多跑。
3. 逐侧边栏执行，按`collectionUnits`的每个对象精确时间窗形成公开查询。`needsQuery=false`不搜。新闻保留市场焦点与多学科两个独立发现阶段，六包按各自进度，不把首轮剩余候选冒充第二轮。
4. 复用已有原帖与事件证据；只有新候选、有实质进展或明确更正线索才追源、独立查反证。无新候选时后两阶段写“无需执行”及原因，不启动空查询。不得为提速降低来源门槛：常规查询和首次纠错只走Grok网页Expert；网页一次针对性补查后仍有明确缺口，才可在额度可用时用Grok Bot定点补查。Bot不得接管整批或重复合格结果，每次运行最多3个独立问题，剩余缺口留待后续。
5. 每批结束先保存`data/collection-runs/<RUN>.json`：顶层`id/cutoff`，`batches`内该页的`output`保存完整待发布结果（新闻含focus/insights，人物/个股/AI含items，确实无新增时可为空数组）；顶层`collectionResults`逐对象保存下列报告。该审计不是私有聊天、凭证或整段浏览器历史。

```json
{
  "runId":"本期运行编号",
  "cutoff":"本轮冻结截止，含时区",
  "results":[{
    "unit":"tickers:mu",
    "start":"该对象上次成功截止，含时区",
    "end":"计划给出的该对象本轮截止，含时区",
    "status":"searched",
    "queries":["实际执行的公开查询"],
    "note":"已执行范围与缺口；不是X全量覆盖",
    "evidenceFile":"data/collection-runs/本期运行编号.json"
  }],
  "pending":[]
}
```

报告的`unit/start/end/status/queries`必须已经原样保存在审计`collectionResults`中。审计`batches`还须包含该对象候选、入选/落选/待核及完整待发布卡片；只有临时提示词、执行计划不能证明成功。将报告保存为本项目文件，执行`npm run collection:progress -- record <REPORT.json>`。每批及时落盘，后批失败不得使前批重新采集；统一在所有批次关闭后提交发布。

6. 新卡片载荷标`collectionMode: incremental-v1`，附计划的`collectionUnits`；新闻事件附`collectionUnit`。旧重点从存量合并，不要求Grok重新搜索24h/7天/30天。人物/个股/AI保留有效旧周榜，仍在近窗但被名额挤出的规则条目放`retainedItems`，不因晚报有新内容删早报重点。
7. 学习按components执行：每天08:00两刊各目标3篇；工作日20:30/周末08:00基础知识与每日5条小知识。每日趣事停用。独立来源和知识点/DOI去重见各SOP，不使用X对象窗口，不因新闻无新增跳过。宏观只查到期/过时，财报按官方例外。
8. 各批关闭后归档和发布。按用户要求不运行本地测试、check、build或预览；明确暂存本次文件、提交推送、核对远端及Cloudflare相关资源。采集进度与发布进度分别记录。失败保留存量和断点，不强推。

## 展示与保留

首页默认“当前重点（累计保留）”，包含当前有效池，而非只有最后一批。标记“本轮新增／本轮有进展／累计保留”；同事件只展示一张当前卡片，时间线保留之前版本。更正、失效保留原卡片、原因及依据，不悄悄消失。

事实展示24h/七天/合集30天只决定阅读范围，不驱动搜索；独立个股热点按其契约每次重搜完整24h。持久池独立于三期快照；周一完整汇总已入库周末事实，只搜索最近成功截止后的余下增量。失败或网页时钟过去不会自行清空内容，不宣称用户已经阅读。

## 耗时记录

日志必须记录各侧栏开始/结束、发现/追源/反证的起止，以及Git和线上核验时间；缓存命中、无候选跳过、重试次数独立记录。普通增量5—10分钟是待观察的工程目标，不是已证明的保证。固定网页检索和模型等待不会随时间窗长度同比缩短。

每批和子阶段在实际操作前后使用`npm run ops:run -- step --period <RUN> --page news --name batch|discovery|source-verification|counter-evidence --status running|ok|failed|skipped --detail "实际情况"`。不要事后补造起点；没有候选的后两阶段直接记skipped，不调用Grok。计时是墙钟跨度，不能冒称纯模型计算时间。
