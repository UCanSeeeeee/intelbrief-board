# 项目工作流 SOP

更新于2026-10-18，北京时间。面向项目所有者、协作者及其LLM，说明功能开发、信息获取、数据填充和网页发布如何衔接。

本文是工作流说明；执行约束以根目录 [AGENTS.md](../AGENTS.md) 为准，当前断点见 [TASKS.md](../TASKS.md)。专题规则通过下方链接引用，不在本文另立一套标准。

## 1. 各方分工

| 参与方 | 职责 |
|---|---|
| 项目所有者与协作者 | 提出需求、共同开发功能，沿用已采用的产品设计和内容标准 |
| 开发LLM | 读取项目规则、同步远端、实现需求、提交推送；展示已有真实数据，缺数据时显示空态 |
| 本机Codex定时任务 | 按侧边栏分批组织检索，结合知识库核验筛选，生成数据并提交发布 |
| Grok网页版 | 当前优先使用的X公开信息检索入口，返回候选、来源和覆盖缺口 |
| Grok Bot「X+github」 | Grok网页版不可用或覆盖不足且Bot额度可用时的后备；当前项目任务因周额度耗尽暂停 |
| GitHub | 保存代码、配置、公开知识库、内容数据与变更历史；共同维护默认分支为 `master` |
| Cloudflare Pages | 接收 `master` 更新后自动构建部署，提供手机和电脑访问的网页 |

网页地址：[intelbrief-board.pages.dev](https://intelbrief-board.pages.dev/)。源码仓库：[UCanSeeeeee/intelbrief-board](https://github.com/UCanSeeeeee/intelbrief-board)。

## 2. 功能维护流程

1. 你或朋友提出具体需求，开发LLM先读 `AGENTS.md`、`CONTEXT.md`、`TASKS.md`，再读取相关页面契约、设计说明和配置。
2. 确认远端、分支及工作区，执行 `git pull --ff-only origin master`，保留他人已有改动。
3. 在需求范围内修改功能和必要文档，沿用现有产品基线。可以直接显示已有真实数据；没有对应数据时显示空态。
4. 修改完成后只暂存本次明确文件，提交并推送 `master`。按2026-10-18决定，默认不运行本地测试、全站校验、构建或预览作为提交前置条件；用户明确要求时再执行。
5. Cloudflare自动构建部署。推送成功与部署成功分别报告；没有线上证据时不声称已经上线。

双方维护同一个仓库，提交前注意远端新改动；并发冲突先比较和整合，不覆盖他人工作、不强推。协作者的开发LLM不另启内容定时器，也不借开发任务顺带编写真实新闻。

## 3. 定时信息获取流程

当前由本机Codex在工作日北京时间 **08:00、15:00、20:30**、周六日 **08:00** 启动。每个时点一次总任务，按侧边栏Tab独立分批；逐对象接上次成功截止，手动与定时共享进度，按[增量采集入口](INCREMENTAL_COLLECTION.md)执行。

执行器先读取当前规则、项目知识库、对应页面配置和已有数据，确定本期截止与时间窗口，检查期次是否已存在，再运行：

```bash
npm run collection:plan -- YYYY-MM-DDTHH:MM:00+08:00
```

`HH:MM` 只能使用本期的 `08:00`、`15:00` 或 `20:30`。批次顺序和模式由 [collection-batches.json](../config/collection-batches.json) 维护：

| 独立侧边栏批次 | 本次处理方式 |
|---|---|
| 美股讯息 | 独立检索市场焦点与知识驱动洞察，最多5条焦点加10条多学科洞察；另运行`npm run fetch:sentiment`维护顶部[CNN情绪卡](MARKET_SENTIMENT.md)非X快照，失败不阻塞新闻 |
| 具体人物 | 按人物和合集的顶部Tab建立子清单，分别覆盖来源与滚动窗口 |
| 具体个股 | 按配置中的股票逐个检索，保留仍符合规则的近窗与周榜内容 |
| AI板块 | 按实验室、产品与其他合集的顶部Tab分别检索 |
| 每日学习 | 工作日20:30、周末08:00：趣事及专业版／18+故事版只复用验收材料；两刊各1篇健康生活[论文](JOURNAL_PAPERS.md)，另生成目标5条[反直觉小知识](COUNTERINTUITIVE_KNOWLEDGE.md)，均不凑数、保留往期 |
| 宏观大事 | 独立检查日历是否到期或过时，按既有低频和官方来源规则维护 |
| 财报日历 | 独立刷新日历并按财报规则处理待评价结果；采用Nasdaq及公司官方披露等已授权来源 |

各批次有独立的上下文、检索清单、提示词、候选、缺口和中间结果，按顺序推进；人物、个股和AI在所属批次内再细分顶部Tab。全站内容不混在一个大提示词中获取，各批次也不并行写同一数据文件。

## 4. Grok检索与信息筛选

X内容优先使用已登录的Grok网页版，只发送当前批次需要的公开问题。网页不可用或覆盖不足且Bot额度可用时，才尝试Grok Bot「X+github」，并记录切换原因。当前Bot周额度耗尽期间不反复重试，也不自动恢复其任务。两条路径均失败时保留旧内容、记录失败和覆盖缺口。

每个X批次先发现候选；只有新候选或实质变化才继续追源与反证，旧证据无变化复用，空候选明确记无需执行，不空跑。需要执行时分为：

1. **发现候选**：围绕本Tab的对象和知识库问题分主题检索，初步去重；普通账号可提供线索。
2. **追查来源**：为拟入选事件追到公司、政府、监管、当事人或可识别权威媒体原帖；保留每个作者对应的真实链接、准确发帖时间、事件时间及关键原文。无法追源的量化陈述、政策状态和高管表态只留在落选或缺口记录。
3. **寻找反证并筛选**：独立查询更正、相反数据和替代解释。Codex结合项目知识库做最终判断，翻译、比较、去重并生成对应页面的数据。

研究优先级为半导体、电力、AI落地。美股讯息的市场焦点与多学科洞察分别检索；第二组使用项目的多学科认知与夜雨知识库，不能拿第一组余料直接补数。

保存作者、原帖链接、发帖时间、事件时间或未知说明、中文事实摘要、影响机制和证据缺口。Grok返回按采集器转述记录；模型判断与来源事实分开。数量通常是上限，证据或价值不足就保留缺额；人物页热度补位例外严格按其专门规则执行。

来源核验、真实性要求与数据契约始终有效；“不需要本地验证再提交”只取消本地测试、全站校验和构建的提交前置条件，不授权编造数据或把未核验的线索当成已证实事实。

## 5. 数据填充与网页发布

各批次处理结束后，由当前同一个运营执行者汇总结果、去重并通过对应页面的数据写入流程落盘，再统一提交推送。已有归档不能覆盖，单个批次失败不能清空其他Tab或已有待阅内容。

流程为：

```text
Codex定时任务
  → 读取规则、知识库和已有数据
  → 按侧边栏Tab分批检索、追源与筛选
  → 写入结构化数据和实际覆盖记录
  → 提交并推送GitHub master
  → Cloudflare自动构建部署
  → 用户通过网页阅读
```

网页是只读看板，没有手动“更新”按钮；手机访问新闻展示已发布数据。顶部CNN情绪卡由Cloudflare只读接口按访问获取并缓存，失败沿用发布快照，不触发新闻任务。周末消息、跨期保留和最近三期快照按照 [北京时间批次规则](TRADING_DAY_READING.md) 处理。

## 6. 新增栏目怎样自动获得数据

开发一个新Tab并不意味着定时任务会自动知道该搜什么。新增栏目需要同时明确：

- 获取哪些对象与来源、覆盖多长时间、什么算值得收录。
- 字段和数据格式、空态、数量上限、去重及旧内容保留方式。
- 将该栏目接入现有批次配置、运营说明和定时流程。

完成接入后，由现有定时任务采集填充。开发LLM可以用夹具进行用户明确要求的测试，不能把夹具、模型编造内容或占位新闻发布成真实信息。

## 7. 当前状态与依赖

本机任务启用，Grok Bot任务、Webhook与探针暂停；已有真实本机到点触发、分批采集及发布样本。连续可靠性、新增量规则效率和失败恢复仍按真实期次观察，证据与边界只在[运营说明](GROK_BOT_OPERATIONS.md)、待推进动作只在[TASKS](../TASKS.md)维护。

本机任务依赖电脑开机、联网和执行环境可用，以及Grok登录、额度和GitHub发布权限正常。任务创建成功不代表每期都能成功发布；失败时按真实阶段留断点并保留旧数据。
